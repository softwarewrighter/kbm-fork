# Bring-up plan: RP2350 (Seeed XIAO RP2350, Raspberry Pi Pico 2)

The RP2350 has two Cortex-M33 cores (with FPU) and two Hazard3 RISC-V cores
(RV32IMAC, no FPU); the chip boots one architecture or the other. 520 KB of
SRAM. Goal: k's REPL on USB serial with the Arm cores first, then the
RISC-V cores, both passing the goldens via `test/drive_serial.py`.

## What is ready

- `boards/mcu/dist/libk-m33-softfp.a`: k for Cortex-M33 + FPU with the
  `softfp` float ABI, which is what the Pico SDK uses for RP2350 Arm
  builds. Verified in QEMU (`m33-an505-softfp-gcc`): GCC-compiled glue
  linked against it passes the goldens.
- `boards/mcu/dist/libk-rv32imac-ilp32.a`: k for the Hazard3 cores
  (soft-float). Passes the goldens in QEMU (`rv32imac-virt`).
- Both use KHEAP=12 (256 KiB heap): about 297 KB of RAM with tables and
  stack, inside the 520 KB.
- `boards/mcu/common/ksys-bare.c`: k's OS layer over `con_getc`,
  `con_putc`, `con_exit`.

## Plan

### 1. Toolchain and a blank project

1. Pico SDK 2.x (RP2350 support), `picotool`, `arm-none-eabi-gcc`; for the
   RISC-V build, a RISC-V GCC the SDK accepts (see the SDK docs). Note
   versions.
2. Build and flash a USB-serial hello world for the board
   (`-DPICO_BOARD=seeed_xiao_rp2350` or `pico2`, `-DPICO_PLATFORM=rp2350`):
   hold BOOT while plugging in, copy the `.uf2` to the RP2350 drive (or
   `picotool load -x`). Confirm `/dev/ttyACM0` appears.
3. Check the float ABI in the build's compile flags
   (`build/compile_commands.json`): expect `-mfloat-abi=softfp`. If it is
   `hard`, use `libk-m33-hard.a` instead.

### 2. Add k (Arm)

```
k_rp2350/
  CMakeLists.txt
  main.c                 starts k
  con_pico.c             the three console functions
  ksys-bare.c            copy from boards/mcu/common/ (NOT libc-min.c)
  libk-m33-softfp.a      copy from boards/mcu/dist/
```

`CMakeLists.txt` (starting point):

```cmake
cmake_minimum_required(VERSION 3.13)
include(pico_sdk_import.cmake)
project(k_rp2350 C CXX ASM)
pico_sdk_init()
add_executable(k_rp2350 main.c con_pico.c ksys-bare.c)
target_link_libraries(k_rp2350 pico_stdlib ${CMAKE_CURRENT_SOURCE_DIR}/libk-m33-softfp.a)
pico_enable_stdio_usb(k_rp2350 1)
pico_enable_stdio_uart(k_rp2350 0)
target_compile_definitions(k_rp2350 PRIVATE
    PICO_STACK_SIZE=0x8000          # k needs ~32 KB of stack; the default is 2 KB
    PICO_STDIO_DEFAULT_CRLF=0)      # ksys-bare.c already sends \r\n
pico_add_extra_outputs(k_rp2350)
```

`con_pico.c`:

```c
#include "pico/stdlib.h"
int  con_getc(void) { return getchar(); }           // blocks until a byte arrives
void con_putc(int c) { putchar_raw(c); }
void con_exit(int code) { (void)code; for (;;) tight_loop_contents(); }
```

`main.c`:

```c
#include "pico/stdlib.h"
void kmain(void);
int main(void) {
    stdio_init_all();
    while (!stdio_usb_connected()) sleep_ms(50);   // wait for the host to open the port
    kmain();
}
```

Waiting for the USB connection means k's banner appears only once the
port is open, which suits `drive_serial.py`.

### 3. Test (Arm)

1. Flash the `.uf2`.
2. `python3 test/drive_serial.py test/golden/basic.k /dev/ttyACM0 | diff test/golden/basic.expected -`
   (the board waits for the port, then prints the banner).
3. Heap limit: `test/limits/heap.k` should end with `wsfull`.
4. Record RAM use from the build (`arm-none-eabi-size k_rp2350.elf`).

### 4. RISC-V cores (Hazard3)

Same project, built for `-DPICO_PLATFORM=rp2350-riscv`, linking
`libk-rv32imac-ilp32.a` instead. Check the SDK's RISC-V `-march`/`-mabi`
in `compile_commands.json`: expect `ilp32` (no hardware float). The SDK's
`-march` may add bit-manipulation extensions (Zba/Zbb...); the library only
uses RV32IMAC, which is compatible. Repeat steps 3.1-3.4.

The library calls `sqrtf` for k's vector square root on FPU-less targets;
the Pico SDK's newlib provides it. (Without a libc, `libc-min.c` provides
a weak one.)

## Stretch: XIAO RP2040 / Pico (RP2040)

Cortex-M0+, no FPU, 264 KB SRAM. Not built or tested yet. It would need a
`libk` for `thumbv6m` soft-float with KHEAP=11 (128 KiB), added as a target
in `boards/mcu/build.sh`; QEMU has no M0+ stand-in with semihosting, so
the first test would be on the board.

## Known gaps / risks

- `\t` timing: `ut` returns 0 on Arm MCUs (no portable cycle counter); fine
  for the goldens. Hook it to the SDK's timer through `k_sys` if wanted.
- Float results are not covered by the goldens (k prints `?.?`).
- If `getchar()` returns `PICO_ERROR_TIMEOUT` (-1) on some SDK version,
  loop on `getchar_timeout_us(...)` until a byte arrives.
