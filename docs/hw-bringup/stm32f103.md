# Bring-up plan: STM32F103C8T6 board ("Blue Pill" class, bare metal)

The STM32F103C8T6 is a Cortex-M3 at 72 MHz (from an 8 MHz crystal), with no
FPU, 20 KB SRAM, and 64 KB flash officially. Boards like the "Type-C ARM
32-bit MCU Minimum System" module have BOOT0/BOOT1 jumpers, a reset button,
an SWD header (3V3, SWDIO, SWCLK, GND), and a USB-C port. The USB-C port is
wired to the chip's USB pins (PA11/PA12). There is no bootloader on it, so
here it only supplies power.

Goal: k's REPL on USART1, passing `test/golden/basic.k`. `big.k` needs
256 KiB of heap and is skipped.

## The port

There is no SDK. `boards/stm32f103/stm32f1.c` (~140 lines) is the whole port:
- reset;
- 72 MHz clock setup, falling back to the internal 8 MHz oscillator if the
  crystal does not start;
- a polled USART1 console on **PA9 (TX) / PA10 (RX)**, 115200 8N1;
- exit: `\\` resets the chip.

k and `boards/mcu/common/ksys-bare.c` do the rest. Build with GCC
(`gcc-arm-none-eabi`):

```sh
boards/stm32f103/build.sh --test   # firmware + QEMU stand-in + goldens
```

| | Size | |
|---|---|---|
| k's heap | 8 KiB | `KHEAP=7`; 16 KiB would not leave room for the stack |
| handles | 1 KiB | `KOBJ=7`: 128 objects |
| other statics | ~1 KiB | |
| stack | 6 KiB reserved | measured peak **3.7 KiB** over basic.k (`KSTACK_REPORT=1`) |
| **RAM** | **16 KB of 20** | the link fails if it does not fit |
| **flash** | **85 KB** | **more than the official 64 KB**; see "Flash size" |

k is compiled with `-Os`. GCC `-Ofast` makes the code larger, and on RV32 it
needed 8.9 KiB of stack (see `ch582.md`).

### Verified here (QEMU)

The firmware is tested on QEMU's `netduino2` (STM32F205, Cortex-M3).
- It is the same code, flags, heap and RAM limit.
- Only the USART1 address differs, and the F1 clock/GPIO setup is skipped,
  because QEMU does not model those registers.
- Results: basic.k passes, heap.k prints `wsfull`, and the stack peak is
  3.7 KiB.

Not verified: the F1 clock and GPIO setup, flash beyond 64 KB, and the board
itself.

## Flash size: the one real risk

k is 85 KB. The C8T6 is specified at 64 KB, but most genuine C8 chips have
128 KB that programs and verifies correctly (they share the CB's die).
Clones (CKS32, GD32, APM32...) vary. The link script assumes 128 KB
(`FLASH_KB=128`). The flash-and-verify step below checks the upper 64 KB
directly.

**If verify fails at or above 0x08010000, stop and report.** The chip really
has 64 KB. Options for the human:
- an STM32F103**CB**T6 board (128 KB, same pinout);
- another board;
- a trimmed k (not designed yet).

## Prerequisites (bring-up machine)

- Build: `gcc-arm-none-eabi` (Debian/Ubuntu), plus `qemu-system-arm` and
  Python 3 for `--test`.
- **A 3.3 V USB-serial adapter** for the console, wired as:
  - adapter TX → **PA10**
  - adapter RX → **PA9**
  - GND → GND
  
  The same adapter can flash the chip through its ROM bootloader (method A
  below).
- One flashing method:
  - **A. Serial ROM bootloader:** `stm32flash` (`apt install stm32flash`).
    No extra hardware is needed.
  - **B. ST-Link V2 (clone is fine) on the SWD header:** `st-flash`
    (`apt install stlink-tools`), `probe-rs` (Rust: `cargo install
    probe-rs-tools`), or OpenOCD.
- Python 3 with `pyserial` for `test/drive_serial.py`.

## Safety (read first)

- **Allowed:** writing and erasing the main flash (all methods below),
  `stm32flash` read/verify, `st-info --probe`, `probe-rs info`.
- **Never, without the human's approval:**
  - set read-out protection or write option bytes (`stm32flash -j`,
    OpenOCD `stm32f1x lock`, any option-byte write);
  - "unprotect" (`stm32flash -k`, `stm32f1x unlock`), which mass-erases.
  
  These are the only steps that can lock you out of the chip.
- **Recovery:** with BOOT0 = 1 the chip always starts its ROM bootloader,
  whatever the flash holds. For SWD, use "connect under reset" (probe-rs
  `--connect-under-reset`, st-flash `--connect-under-reset`).
- Work on branch `hw/stm32f103` off `spike/portable-k`; commit and push results.

## Steps

### 1. Build

```sh
boards/stm32f103/build.sh --test
```

Expect `flash=85 KB`, `RAM=10 KB + 6 KB stack of 20`, `PASS basic.k`, and
`PASS heap.k`.

### 2. Identify the chip

Use **A**: put the BOOT0 jumper on 1 (BOOT1 on 0), press RESET, then
`stm32flash /dev/ttyUSB0`. Or use **B**: `st-info --probe` or `probe-rs info`.
- Record the device ID and flash size reported. The C8 reports 64 KB from
  its flash-size register even when it has 128 KB.
- Read the chip marking under a light: STM32, CKS32, GD32, APM32...
- A clone may report an unexpected ID. With OpenOCD that shows as
  "UNEXPECTED idcode"; add `-c "set CPUTAPID 0"`.

### 3. Flash and verify (the 128 KB check)

**A. Serial bootloader** (BOOT0 = 1, then press RESET):
```sh
stm32flash -w boards/stm32f103/build/k-stm32f103.bin -v -g 0x08000000 /dev/ttyUSB0
```
If stm32flash refuses an image larger than its idea of the flash size, use
method B. Then set BOOT0 back to 0 and press RESET.

**B. ST-Link (SWD)**, any one of:
```sh
st-flash --flash=128k write boards/stm32f103/build/k-stm32f103.bin 0x08000000   # verifies by default
probe-rs download --chip STM32F103CB --binary-format bin --base-address 0x08000000 \
    boards/stm32f103/build/k-stm32f103.bin --verify && probe-rs reset --chip STM32F103CB
openocd -f interface/stlink.cfg -c "set FLASH_SIZE 0x20000" -f target/stm32f1x.cfg \
    -c "program boards/stm32f103/build/k-stm32f103.elf verify reset exit"
```
Telling each tool that the chip has 128 KB is deliberate:
- `--flash=128k`, `--chip STM32F103CB`, and `FLASH_SIZE` override the
  64 KB the chip reports.
- The verify then proves that the upper half exists. If it fails, see
  "Flash size".

### 4. Smoke test

```sh
python3 -m serial.tools.miniterm /dev/ttyUSB0 115200    # Ctrl-] quits
```

Press RESET (BOOT0 = 0). You should see the banner `... (c)arthur
whitney(l)MIT`. Then:
- `1+2` → `3`
- `3^!10` → three rows
- `\\` → the chip resets into k

**Garbage text** usually means the clock and baud rate disagree. The code
picks 72 MHz only if the crystal and PLL come up. Note what you saw.

### 5. Acceptance

```sh
python3 test/drive_serial.py test/golden/basic.k /dev/ttyUSB0 | diff test/golden/basic.expected -
```

Start the command, then press RESET within 60 s. The adapter's RTS is not
wired to RESET, so `--reset` does nothing. Use `--attached` if k is already
at its prompt.

Heap limit:
`python3 test/drive_serial.py --attached test/limits/heap.k /dev/ttyUSB0 | tail -2`
should print `wsfull`, then the chip resets.

Stack check on silicon:
1. Rebuild with `KSTACK_REPORT=1 boards/stm32f103/build.sh`, then reflash.
2. Run basic.k, then type `\\`.
3. Record the printed `stack high-water bytes`. In QEMU it was 3708; it
   must stay under STACK = 6144.

## Known gaps / risks

- **Flash > 64 KB:** see "Flash size".
- **Clone chips:** a GD32 runs this code, but its flash wait states and
  maximum clock differ. If it is unstable at 72 MHz, comment out the PLL
  switch in `clock_init` so it stays at 8 MHz, and record what happened.
- **`\t` timing:** it reads `rdcycle`-style counters written for other
  CPUs and is not meaningful here. Do not use it for performance claims.
- **Floats:** they are soft-float (no FPU). k prints them as `?.?`, so the
  goldens cannot see them.
